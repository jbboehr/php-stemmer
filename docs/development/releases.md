# PIE binary releases

CI builds 25 archives with Nix for PHP 8.1–8.5. All binaries are non-debug
builds, with Snowball 2.2.0 linked statically:

| Platform | Architecture | Thread safety | Build host |
| --- | --- | --- | --- |
| Linux, glibc | x86_64 | NTS | Linux |
| Linux, musl | x86_64 | NTS | Linux |
| macOS | arm64 | NTS | Apple Silicon macOS |
| Windows | x86_64 | NTS and ZTS | Linux, using xwin |

The recipes live in `nix/release/`. For example:

```sh
nix build .#release-php85-linux-glibc
nix build .#release-php85-linux-musl
nix build .#release-php85-windows-nts
nix build .#release-php85-windows-ts
# On an Apple Silicon Mac:
nix build .#release-php85-darwin
```

Each output contains a PIE-compatible ZIP and test support files outside the
ZIP. Only the ZIP is published. ZIP timestamps and permissions are fixed for
reproducibility. Linux binaries have no RPATH and require only their system
libc. macOS builds require an arm64 Mach-O binary and reject Nix paths in its
load commands. Windows compiler
labels match the official PHP SDKs pinned in `nix/windows/php-versions.json`.

The Unix recipe compiles against Nix PHP's NTS headers, including for musl,
using the target libc's compiler and static Snowball library. Nix extracts each
Unix archive and runs all five PHPT tests, including the full Snowball corpus,
with a matching PHP runtime. The musl runtimes include only the CLI and zlib.
All ten Windows DLLs run the same suite under headless Wine in Nix.

Three native CI jobs test the PHP 8.5 archives outside Nix: Linux with the
official Debian and Alpine PHP images, arm64 macOS with setup-php, and Windows
with both NTS and ZTS installations. They check the PHP configuration and
extension version, then run the four API PHPT tests. The existing Debian and
Fedora Docker jobs independently build and test the extension from source.

The remaining CI checks live in Nix, including the PHP/compiler matrix,
Valgrind for PHP 8.1–8.5, coverage generation, and an offline PIE source build.
The additional recipes are in `nix/ci/`. Actions uploads the coverage report to
Codecov and Coveralls after the Nix coverage check succeeds.

## Publishing

1. Update the version and release date in `php_stemmer.h` and commit the changes.
2. Push a stable tag named `vMAJOR.MINOR.PATCH` that matches the extension version.
3. Let the `ci` workflow finish. Its generated Nix matrix builds, checks, and
   uploads the archives. The Docker and three native jobs must also pass.
4. After successful tag CI, the `Release` workflow checks the tag's commit and
   extension version, downloads that run's archives, and publishes the ZIPs
   and `SHA256SUMS` with `gh release create`.

The release workflow must be present on the repository's default branch before
a tag is pushed. Branch and pull-request builds do not publish releases.
Keep release tags fixed during publication. Existing releases are never
overwritten; remove an unfinished draft before retrying a failed publication.
If CI needs retrying, rerun **all jobs** to refresh the complete artifact set.
Artifacts expire after 14 days; rerun CI if they have expired.

Nix caches speed up CI builds. Publication reuses the tested archives directly
and does not rebuild them. PIE falls back to a source build on Unix when no
compatible binary is available; Windows requires a matching binary.

The CI matrix is generated by `nix/github-actions.nix` from the flake checks.
Each release package carries its PHP version, platform, thread safety, and
artifact name as CI metadata. Archive builds validate their own ZIPs and are
also exposed as flake checks. CI uploads those outputs, and the three native
jobs download the PHP 8.5 artifacts from the same run.

## Local verification

```sh
nix flake check -L
nix build .#checks.x86_64-linux.coverage
nix build .#checks.x86_64-linux.php85-valgrind
nix build .#checks.x86_64-linux.pie
# Requires Docker; run from the repository root after building the archive:
nix build .#release-php85-linux-musl
bash .github/scripts/test-release.sh result 8.5 linux-musl
```

The Linux host cannot execute the macOS or native Windows CI jobs. A successful
GitHub CI run is required before the release workflow will publish anything.
